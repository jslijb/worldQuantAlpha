# 相关性墙破法（实战记录）

> 来源：项目 0910–0915 的实测记录 + 平台规则
> 这是本项目唯一真正的瓶颈——**质量关（S+F≥4.0）能挖出 460 条，但相关性关卡住 90%**

---

## 一、规则本身

| 项 | 内容 |
|---|---|
| 触发条件 | `selfCorrelation ≥ 0.7` 触发 Production Correlation 测试 |
| 通过条件 | **max corr < 0.7** **或** Sharpe 比相关 alpha 高 **10%** |
| 豁免线 | `1.10 × max(所有 corr≥0.7 对手的 Sharpe)`，候选 S 达线即可提交 |
| 计算对象 | **当前已提交池**（实时计算，非历史快照） |

---

## 二、最关键的一条性质：相关性是动态的

**实测**：同一个表达式，预检 corr 从 **0.616 → 0.9879**，只因中途提交了两个结构相似的因子。

**机理**：self-corr 是对"当前已提交池"实时算的 → 每提交一个因子，结构相似的兄弟因子 corr 立刻被顶高。

**三条推论**：
1. 提交后必须对剩余池**重新预检**，旧结论全部作废
2. 同构候选**严禁扎堆**提交
3. 必须常备多套**结构不同**的 PNL 储备

## 七、提交流程（含并发注意）

1. 质量闸门：S+F ≥ 4.0 且 testS ≥ 1.25 且 checks 无 FAIL
2. corr 预检：`GET /alphas/{id}/correlations/self`
3. 判定：max corr < 0.7 → 直通；否则算豁免线 = 1.10 × max(所有 corr≥0.7 对手的 S)，候选 S 达线也可提交
4. `POST /alphas/{id}/submit` → `GET /alphas/{id}` 核 `status == ACTIVE` → 追加台账

**并发警告**：同账号并发提交会互堵（0914 实测 w95_a/w96_a/w96_b/w101_e 四个 POST 201 后永不裁决，w101_f 秒过）→ **必须串行提交**。

### 8.1 事实

**结论**：`200 + Retry-After + 空 body` 的语义**确实是"平台正在现算"、不是故障**（这一点 0915 的修正方向对），
但当前的实情是 **相关计算在账号侧排队积压**，不是 3~4 次轮询就能出。90~180 秒量级都拿不到。

### 8.2 能确凿拿到 corr 数值的唯一路径：提交成功后读 `is.selfCorrelation`

实测对照：

| alpha | 动作 | `GET /alphas/{id}` | `is.selfCorrelation` |
|---|---|---|---|
| `akLp3pzW`（w122_a，0.5 降权版） | 盲提交 POST → ACTIVE | status=**ACTIVE / stage=OS** | **0.8036** ← 数值只能这样拿到 |
| `883wqwVX`（w122_b，0.35 降权版） | 盲提交 POST 200/201 | 提交状态轮询 **59 轮（~8 分钟）status 全为空** → 未裁决 → 仍 UNSUBMITTED | 无 |

⚠️ **一条重要的反向修正（本轮差点写错，已用对照验证）**：
`is.checks` 里的 `SELF_CORRELATION = PENDING` **不是"提交触发了计算"的信号**——
它是**所有未提交 alpha 的默认占位符**。对照 5 条**从未触碰过**的候选，全部一样：

```
O0r3epMg / le8mxdn7 / 3q9NMgk6 / 6XrkW6R5 / KPOAOXEE   → 全部 checks=8 条，SELF_CORRELATION=PENDING
```

所以 **不能**用它判断"提交是否把计算推上去了"，也不能用它当"服务在算"的证据。
真正有判别力的是：**alpha 变成 ACTIVE 之后**，`is.selfCorrelation` 才有值。

**由此得到的操作结论**：
- 想要 corr 数值 → 先让 alpha 提交成功，再读 `is.selfCorrelation`；
- 未提交状态下，除 `correlations/self` 外**没有别的取数入口**，而该端点当前取不到数；
- ⛔ **不要再靠 `correlations/self` 反复打**：一条候选动辄上百次请求，纯粹加剧本已积压的相关计算队列
  （0915 本轮实测：探针 ~102 次 + corr_only ~276 次，之后相关端点始终无 records）。

### 8.5 判决机制定案（0916 上午，推翻 8.2/8.3 的"排队"解读）

8.2/8.3 写于假象之中。真相：

1. **判决从来 4~9 秒就出**：`POST /alphas/{id}/submit`（201）→ 轮询 `GET /alphas/{id}/submit`：
   `200 + Retry-After + 空 body`（计算中，约 4 秒）→ **`403 + {"is":{"checks":[...]}}` = 判决书**。
2. **`blind_submit.py` 的 bug**：判决书顶层是 `is.checks`，没有 `status`/`stage` 键；脚本只认后者，
   把判决当空数据丢弃 → 空转 59 轮报"假 PENDING"。0914~0915 两天的"互堵/积压/服务不可用"叙事**全部由此而来**。
3. 判决书在端点有时效，过期 GET 返回 404——**重新 POST 即可再取判决**（58QPEeOM 实证，两次 POST 均被受理）。
4. alpha 对象的 `is.checks.SELF_CORRELATION` 恒为 PENDING（未提交时的默认占位符），**判决只出现在 submit 端点**。

**正确工具**：`src/submit/submit_v3.py`（解析 403 判决，裁决落 `SUBMIT_VERDICTS.csv`）+ `run_queue_v3.py`（串行队列）。
`correlations/self` 端点、blind_submit.py 均弃用。

### 8.7 ★ 判决书里有「对手明细表」——豁免线必须逐条算（0916 下午，本轮最重要发现）

8.6 把豁免线当成全局常数（"0mR2K6lr 3.45 → 3.80"），**这是错的**。403 判决书里除 `is.checks` 外还有
`is.selfCorrelated.records`，**逐条列出撞到的每个 alpha 的 id / 相关系数 / Sharpe**：

```
selfCorrelated.schema.properties = [id, name, instrumentType, region, universe,
                                    correlation, sharpe, returns, turnover, fitness, margin]
```

实测两条（`src/submit/verdict_dump.py` 落盘 `_autologs/verdict_{alpha_id}.json`）：

| 候选 | 撞到的对手（corr / Sharpe / 单条豁免线 1.1×S） | max corr |
|---|---|---|
| w103_g `LL9YRO2e` | **0mR2K6lr 0.9719/3.45→3.795**；e79PvPpE 0.9485/3.13→3.443；N1QJPJE8 0.7711/2.47→2.717；6Xr2eQaJ 0.7445/2.27→2.497；E5vx6NJP 0.7342/2.45→2.695 | 0.9719 |
| w132_h `78N8nA6L` | **kqoq0zed 0.9339/2.02→2.222**；6Xr2eQaJ 0.7544/2.27→2.497；akLp3pzW 0.7031/2.78→3.058；e79PvPpE 0.7016/3.13→3.443 | 0.9339 |

**三条硬结论**：

1. **豁免线 = 1.10 × max(所有 corr≥0.7 对手的 S)**——只要有一个高 S 对手也 ≥0.7，它就绑住你。
   w132_h 看着像"只差 kqoq0zed 的 2.22"，实际被 e79PvPpE(S3.13) 绑到 **3.443**，等于没戏。
   **单个低 S 对手救不了你。**
2. **同骨架兄弟会被最新入池的那个顶穿**：w132_h 首判 0.7544，kqoq0zed 入池后重判 **0.9339**。
   这是"一个配方只能吃一口"的第三次实证——**同族候选必须换几何，不是换参数**。
3. **提交即测量**：每条候选一次 POST 就能拿到完整对手表（3~5 秒、2 个请求），
   不必碰 `correlations/self`。**改完候选立刻测 corr，不要攒着**。

**工具**：`src/submit/verdict_dump.py <alpha_id> [cid]` —— 落盘完整判决书 + 打印对手表（按 corr 降序 + 逐条豁免线）。

## 8.9 0916 晚：本地双工具上线 + 腿库饱和（当天 10 条高质量、历史欠账清零）

### 工具一：`src/analysis/pnl_corr.py` —— 免提交算 self-corr
- `GET /alphas/{id}/recordsets/pnl` 返回**累计 PnL** → 必须先差分成日 PnL（不差分则任意两条都 0.99 相关）。
- 差分后本地算的 max corr 与平台判决误差 **±0.02**（平台 ≈ 本地 **+0.006~+0.017**）→ **判直通留缓冲：本地 ≤ 0.685**。
- **价值**：不提交、不污染池子即可筛任意候选 → 456 条历史积压 **12 分钟筛完**，直接命中 `le8EAJLO`（SF4.24）入池。

### 工具二：`src/analysis/leg_lab.py` —— 腿库离线拼装
- 前提：alpha 信号 = Σ wᵢ·group_rank(腿ᵢ)，subindustry 去均值与 decay 都是线性算子 → `PnL(Σwᵢ腿ᵢ) ≈ Σwᵢ·PnL(腿ᵢ)`。
- 只跑单腿建库（batch156 起共 46 条腿），任意权重组合离线算 S 与 corr（numpy 向量化 `corr = Mmat@w / √(wᵀGw)`）。
- **战果**：`pwRwWoJ3`（**SF 6.91** / tS 2.25）、`O0N0R5NY`（5.47）、`9qjqm3Q9`（5.69）、`LLNL3qqm`（4.22）、`QPbP6aRQ`（4.57）等一批当天入池。

### ⚠️ 三条必须记住的坑
1. **线性预测会系统性低估 maxcorr**：实测「预测 PnL vs 实测 PnL」corr 只有 **0.83~0.96** → 预测的 maxcorr **偏低 +0.05~+0.19（均值 ≈ +0.12）**。按 0.66 阈值搜出的 19 条（w162/w164）实跑后真实 corr 是 0.71~0.84，**只过 1 条**。
   → **判据：搜索阈值压到 `--max-corr 0.55~0.57`；实跑后必须 `pnl_corr.py` 实测复核才提交。leg_lab 是候选生成器，不是判决器。**
2. **池子只能取自台账**：不得从 `pnl/` 缓存目录取"池子"（混着数百条未提交候选/实验腿 → max corr 虚高压死，曾搜出 0 个可用组合）。
3. **S 必须用原始日 PnL 算**（先扣均值则均值≈0、S 恒为 0）；G 与 Mmat 必须同尺度。
